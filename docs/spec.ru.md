# Open Behavior Protocol 0.1

## Назначение и граница

OBP представляет предметное поведение: участников, значения, действия, выбор, формулы, состояния, правила, примеры и свойства. Модель описывает то, что должно происходить или что наблюдается по коду, независимо от устройства конкретной среды. Бизнес-важная формула тарифа относится к поведению; HTTP-маршрут, устройство базы или вызов библиотеки — к реализации. Требование об отсутствии сети может быть предметным, если продукт обещает такое поведение; конкретный механизм повтора остаётся в среде.

Одна модель может связываться с несколькими реализациями. `basis.kind=requirement` обозначает требование, `code` — вывод из кода, `mixed` — оба источника, `unknown` — происхождение не установлено. Вывод из кода описывает обнаруженное поведение, а не подтверждённое намерение бизнеса. Связь и хеш источника не доказывают, что реализация ему соответствует.

В 0.1 модель процесса использует схему `version: 1`. Файл может содержать один проект и несколько процессов либо отдельные процессы без проекта. Внешний ID процесса в объявлении, локальные ID элементов и ID объектов реализации имеют разные области назначения; не следует присваивать новые ID при простом преобразовании формата.

## Текст и грамматика

Исходник — UTF-8 текст `.obp`. Ключи объектов допускают идентификатор или строку JSON; значения имеют синтаксис JSON. Допускаются комментарии `//` и `/* … */`, `,` или `;` как разделители и завершающий разделитель. Строки, числа и управляющие символы имеют правила JSON. Ключи в одном объекте и ID процессов не могут повторяться. Неизвестные поля модели отклоняются валидатором.

```ebnf
document = "obp" "0.1" ";" declaration { declaration } ;
declaration = project | process ;
project  = "project" ( identifier | string ) object [ ";" ] ;
process  = "process" ( identifier | string ) object [ ";" ] ;
object   = "{" [ member { separator member } [ separator ] ] "}" ;
member   = ( identifier | string ) ":" value ;
array    = "[" [ value { separator value } [ separator ] ] "]" ;
value    = object | array | string | number | "true" | "false" | "null" ;
separator = "," | ";" ;
identifier = ( letter | "_" ) { letter | digit | "_" | "-" } ;
```

`parse` возвращает позиции в UTF-16: смещение с нуля, строки и столбцы с единицы. Позиции доступны по JSON Pointer внутри `locations`. `format` сохраняет данные, но не комментарии и исходные пробелы. Двоичный CBOR используется только для передачи результатов API, а не как текстовый исходник.

## Проект и среды

Необязательный `project` содержит `title`, массивы `modules`, `entities`, `environments`, `implementations` и необязательный `description`.

- Модуль содержит `id`, `title`, `processes`, `dependsOn` и необязательный `description`. Процесс из документа может принадлежать одному модулю; для обращения к другому модулю используется `dependsOn`, а не копия процесса.
- Сущность содержит `id`, `title`, `moduleId` (`null` для общей сущности), необязательные `description` и `dataSchema`. Её схема — те же типы данных, что у факта `data`. Сущность и сгруппированные факты отдельного процесса связывает хост; одинаковые названия не создают связь автоматически.
- Среда содержит `id`, `title`, `kind`, массивы `technologies` и `architecture`, необязательный `description`. Тип задаётся строкой, чтобы описывать приложение, сервер, библиотеку или другую среду без закрытого списка платформ.
- Реализация содержит совместимый 36-символьный `id`, `title`, `environmentId`, массив относительных `codeRefs` и необязательный `description`. Фактическое чтение файлов и проверку их версий выполняет хост. Блок процесса ссылается на реализацию через `bindings`.

ID уникальны внутри каждого вида; ссылки модуля на объявленные в документе процессы и зависимости, сущности на модуль и реализации на среду проверяются. Если реализация из `bindings` не объявлена в документе, выдаётся предупреждение: хост может разрешить внешнюю ссылку. Сама привязка не доказывает выполнение процесса реализацией. Пример с одной моделью и тремя средами — [publish-article.obp](../examples/publish-article.obp).

## Структура процесса

Обязательные поля — `version`, `intent`, `basis`, `assumptions`, `facts`, `steps`, `definitions`, `properties`, `examples`, `bindings`. Дополнительно допустимы `entities` и `instances`.

- `facts`: именованные значения с `id`, `title`, `type`, `initial` и необязательной областью `scope=shared|instance`. `initial.kind` — `value`, `any` или `unknown`. `any` означает любое допустимое значение, а `unknown` — нехватку данных, не произвольное значение.
- Типы: `boolean`, `choice`, `text`, `integer`, `decimal`, `date`, `instant`, `collection`, `data`. Варианты `choice` задаются `options`; коллекция описывается `fields`; рекурсивное `data` — `dataSchema` с именованными определениями и `root`. Целые и дробные значения передаются строками, логические — булевыми значениями. Дата — `YYYY-MM-DD`; время — UTC `YYYY-MM-DDTHH:mm:ssZ`.
- `entities`: предметные группы существующих значений, опционально связанные с объектом карты через `nodeId`. Факт не может входить сразу в две такие группы.
- `steps` и `definitions`: последовательности блоков с устойчивыми ID. Локальные определения могут повторно использоваться через `use`; `call` ссылается на определение другого процесса, его версию и сопоставление параметров. Хост обязан разрешить внешнюю ссылку до проверки такого фрагмента.
- `properties`: утверждения `always`, `after`, `eventually`, `within`. Выражение может быть неопределённым; `within` задаёт начало, конец, факт времени и предел секунд.
- `examples`: начальные значения, последовательность ID действий, при необходимости промежуточные состояния, ожидаемые значения и признак завершения.
- `bindings`: пары `blockId` / `implementationId`. Допускаются привязки одного блока к разным средам; смысл реализации, её версия и проверка достоверности принадлежат хосту.

ID фактов, сущностей, блоков, ветвей, определений, свойств и примеров внутри модели уникальны; они состоят из 1–64 символов, начинаются со строчной латинской буквы и далее содержат `a-z`, цифры, `_` или `-`. ID скалярных фактов и полей коллекций дополнительно ограничены 32 символами и допускают только `a-z`, цифры и `_`. В совместимом профиле ID связанных объектов и внешних процессов — строки из 36 шестнадцатеричных символов и дефисов. Они не являются проверкой существования объекта.

## Блоки и выражения

`action` содержит `actor`, `guard`, `specified` и массив `changes` с `factId` и выражением. Все изменения одного действия вычисляются по состоянию до действия и применяются одновременно. `guard: null` или `specified: false` обозначает неготовую модель.

`group` — последовательность; `choice` — набор ветвей с условиями и не более чем одной ветвью `otherwise`; `parallel` — ветви, действия которых могут чередоваться; `repeat` — повтор пока условие истинно. Если `exclusive=true`, пересечение активных ветвей сообщается как проблема. `use` раскрывает локальное определение. Рекурсивные общие блоки не поддерживаются. В `call` неразрешённая внешняя версия остаётся неизвестной, а не пропускается.

Выражения структурированы через `op`: литералы, `var`, `if`, арифметика и сравнения, логические операции, работа с текстом, датами, коллекциями и вложенными данными. `hole` — неизвестное выражение. В `and`, `or` и `if` вычисляются только необходимые ветви. Десятичные литералы преобразуются в точные рациональные числа. Деление на ноль, некорректный путь и переполнение — ошибка вычисления, а не успешная проверка. Целочисленное деление и округление требуют режима. Для `all_items` пустой список удовлетворяет условию; непустоту нужно выразить отдельно. Полный набор операций и типов представляет `Expression` в `src/business-algorithm.ts`; схемы рекурсивных данных — `DataType` в `src/business-data.ts`.

## Проверка и ограничения

Проверка типов не доказывает свойства. Исследование состояний рассматривает описанные действия и все допустимые чередования в исследованной области. `always` проверяется во всех достижимых состояниях, `after` — после действия, `eventually` — на всех рассмотренных путях, `within` — по явно меняемому моделью времени. `may_wait` допускает бесконечное ожидание доступного действия; `advance` предполагает некоторый доступный шаг, но не справедливость каждой ветви. Время не движется само по себе.

Отчёт указывает `complete`, область, число состояний и переходов, возможные нарушения и статусы `verified`, `violated`, `unknown` или `not_applicable`. Пример подтверждает только указанный путь. Если полный перебор невозможен, отдельный инвариант может быть доказан диапазонами, индукцией или необязательным SMT; метод и допущения указываются в результате. Это не доказывает завершение, отсутствие ошибок и соответствие исходному коду. Отсутствие контрпримера в неполном исследовании не является доказательством.

Текущая эталонная реализация ограничивает модель 500 000 символами JSON; допустимы до 64 фактов, 250 блоков, 64 свойств, 32 примеров, 200 привязок; вложенность блоков — до 12. Задаётся до 10 000 запусков, но проверяющий механизм разворачивает не более 64; по умолчанию исследуется до 5000 состояний и 2048 начальных сочетаний. Эти пределы относятся к реализации, а не к продуктовым требованиям. Рекурсивные данные конечны, а их проверка ограничена ресурсами. Ограничение или неизвестная часть дают неполный результат. Доказательства дробей используют рациональные числа, а не семантику вычислений IEEE-754 реального кода. Доступные операции и дополнительные пределы перечислены в [инструкциях для моделей](agent-guide.ru.md).

## Проверка реализаций

`verifyRefinement` сравнивает две формальные модели по явному сопоставлению фактов и действий, исследуя конечную область и достижимые пути. Внутреннее действие реализации не должно менять наблюдаемые значения. `verified` относится к указанному сравнению моделей, а не к реальному приложению.

Node-адаптер `checkImplementationExamples` принимает `command`, `args`, `cwd` и, при необходимости, явно заданный `env`. Для каждого примера он передаёт на stdin один JSON-объект `{caseId, initial, actions}`; ожидаемые ответы не передаются. Адаптер выполняет наблюдаемые действия и возвращает на stdout один JSON-объект `{caseId, initial, states, final, completed}`, где `states` содержит состояние после каждого действия. Адаптер сам отвечает за вызов реальной реализации. Невозможность запуска или неполный ответ дают `unknown`. Даже успешный пример не доказывает остальные пути и достоверность адаптера.

## Совместимость и расширение

`fromModel` и `toModel` сохраняют все допустимые поля модели версии 1, включая ID, ссылки, источники и неизвестные значения. Хост хранит версии и проекты, связывает файлы, выполняет контроль доступа и разрешает внешние определения. OBP не делает сетевых запросов и не запрашивает секреты автоматически; вызывающая сторона отвечает за защиту передаваемых данных. Изменение требований, исходников или привязок не обновляет модель автоматически; хост должен отмечать устаревшие результаты проверки. Неизвестные обязательные расширения и будущие версии нельзя считать поддержанными.
